# FetchKit v1 落地计划

日期：2026-10-26。基线提交：`ab1f46b`（`chore: 初始化 FetchKit SDK 工程骨架`）。

本计划以 [v1-design.md](v1-design.md) 为需求与架构基线，将目标拆解为可以逐项实施、验证和交付的工作。本文中的新增文件、API

## 2. 交付边界与实施原则

首版完成 HTTP/HTTPS 普通文件下载、可靠续传、持久化恢复、完整性校验、任务调度、资源存储和 Android
接入。多连接分段、媒体清单编排、DRM、解压安装等继续排除在首版之外。

贯穿所有阶段的约束：

1. C++ 决定任务状态、续传、重试、写盘、发布和缓存策略；网络后端只负责传输，Android 系统调度只提供执行机会。
2. 最终响应头未经核心接受，不写响应体；收到 200 不能追加到旧文件；416 不能直接判定完成。
3. 只有记录与最终文件一致、且完成所需验证的 Completed 资源才能被 `acquire`；下载中的路径不作为可用资源返回。
4. `received_bytes`、当前文件大小与 `committed_offset` 分开记录；恢复只信任已提交前缀。
5. 同一存储目录单进程所有权，同一资源身份只有一个写入者；过期 generation 的事件不能改变新一轮状态。
6. 线程、数据缓冲和事件队列有上限；不能以文件大小为单位分配内存。任务索引与列表查询另设分页和数量限制。
7. 凭证默认不持久化、不写日志；平台后端关闭缓存、透明解码和自动策略行为，统一由核心判断。HTTP
   需显式开启并受宿主网络安全策略约束。
8. 每阶段交付可运行的纵向链路，协议和故障用例随实现进入，不留到 M5 集中补齐。

构建组织要求：

- `fetchkit::core` 继续作为调用方链接入口；内部目标依赖保持单向，核心状态机通过接口调用传输与存储，避免相互链接形成环。
- 增加 `FETCHKIT_BUILD_TESTS`、`FETCHKIT_WITH_CURL` 等显式选项。Android 平台后端构建不查找 libcurl；启用
  curl 却缺少依赖时明确失败。
- 根工程通过 CTest 注册主机测试；测试框架、服务器和 CLI 不进入 AAR。测试依赖及 libcurl 的精确版本、来源、哈希和许可证在
  M0/M1 锁定。
- Linux 是下载参考实现与完整故障测试平台。Windows 保留现有核心/CLI 编译烟测；Windows 下载、锁与掉电语义不新增为
  v1 产品承诺。
- M5 增加安装与 CMake package 导出，验证从安装目录构建外部示例，避免示例只能在源码树内使用核心。

## 4. 先冻结的接口与语义

M0 输出 `docs/transport-contract.md` 和 `docs/api-contract.md`。接口先满足 M1 最小闭环，完整任务与存储
API 分阶段开放，不一次性实现全部空接口。

### 4.1 网络契约

契约至少规定单次请求、operation handle、最终响应头决策、数据块、结束原因和取消完成通知：

- 一次 operation 只执行一次请求；重定向、鉴权刷新和普通重试由核心新建 operation。
- 响应信息保留重复头、状态码、最终 URL、内容编码、消息边界与传输错误；区分正常结束和截断。
- 响应头建立接受屏障；网络线程等待核心决策时不能阻塞核心控制队列，取消必须能唤醒屏障与背压等待。
- 数据块约定只读、长度上限和有效期；若回调返回后失效，跨线程消费前必须复制到有界缓冲或显式转移所有权。
- 暂定每任务最多两个 64 KiB 数据块在队列中；消费者慢时生产端等待，取消与关闭可打断等待。最终参数按 M0
  实测确定。
- `cancel` 可重复调用；只有后端确认 I/O 停止且不再访问缓冲后才回收 handle。operation 结束通知最多一次。
- 每个回调携带任务和 generation；控制层丢弃旧事件，但仍完成对应资源释放。
- M0 同时验证 Linux 阻塞读取的取消方案，不能依赖“有数据时才触发”的回调来承诺停顿连接的取消延迟。
- Android 探针包含宿主已配置全局 Cookie/鉴权处理器的情形，验证其不会绕过核心的凭证隔离与刷新策略；无法控制的行为列为后端契约风险。

### 4.2 API、线程与资源身份

| 主题         | 落地决策                                                                                                                                                                               |
|--------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| C ABI        | opaque engine/task/subscription/lease handle；状态码与附加错误；结构版本/大小；显式释放函数；文档规定字符串和事件生命周期                                                              |
| C++ / Kotlin | C++ RAII 包装 C handle；Kotlin 类型化 request、snapshot、event、error 和可关闭 lease；保留 `FetchKit.version()`                                                                        |
| 线程         | API 提交命令到核心队列；同任务状态串行；I/O 与摘要计算在有界工作线程执行；用户回调由指定 executor 分发且不持锁                                                                         |
| 事件         | 单任务有序；进度可合并；状态与终态不可丢弃；每次运行至多一个终态。暂停不算任务完成；恢复后增加 generation                                                                              |
| 身份         | namespace + resource_key + version + representation_key 共同确定资源；文件名由内部映射生成，不能由远端路径直接拼接                                                                     |
| 重复请求     | 相同身份共享一个持久化任务和写入者，返回独立订阅；长度/可信摘要等约束冲突时明确拒绝，不以最后一次请求覆盖                                                                              |
| 共享控制     | 建议 `cancel(subscription)` 仅撤销该订阅，最后一个订阅取消时才取消共享下载并清理暂存；`pause/resume` 按共享 task 生效并通知全部订阅者。M0 冻结命名与权限，避免一个调用方取消其他订阅者 |
| 进程恢复     | 恢复的是持久化任务，旧订阅与回调不复活；宿主重新绑定并明确允许调度后启动。重启后不因“没有内存订阅者”直接删除恢复任务                                                                   |
| 暂停与关闭   | Paused 事件前完成取消 I/O 和检查点；关闭拒绝新命令、停止 I/O、尽力提交、排空内部资源。关闭等待不能依赖宿主 executor 执行用户回调                                                       |
| 请求提供入口 | 通过业务引用按需取得 URL/鉴权信息，限定超时、刷新次数和取消行为；跨 origin 重新向宿主请求凭证，旧请求信息不隐式沿用                                                                    |
| 租约         | `acquire` 返回只读资源与 lease；显式关闭释放；SDK 关闭不能使仍有效的租约指向可被立即淘汰的文件，具体等待/延迟销毁语义在 M0 固定                                                        |

错误保留设计中的
Network、Timeout、HttpStatus、AuthRequired、ProtocolMismatch、IntegrityMismatch、DiskFull、PermissionDenied、CacheQuotaExceeded、Busy、Cancelled；补充参数非法、对象不存在、SDK
已关闭和元数据不兼容等本地失败的映射。HTTP 状态、系统错误和“是否允许重试”作为结构化字段，不依赖解析错误字符串。

### 4.3 存储布局与记录

M0 定义记录字段，M2 冻结首版格式与兼容策略。建议同一受管根目录下采用 `tmp/`、`objects/`、`records/`
和目录锁文件；具体文件名为内部身份映射。三类目录必须处于同一文件系统。

- 记录包含设计要求的身份、业务地址引用、预期长度/摘要、强校验器、committed_offset、状态、格式版本与记录校验值，另含
  pin、访问时间、可选过期时间、重试预算和发布时间等恢复所需字段。
- 使用有版本、字段长度上限、记录总长上限和校验值的独立记录；M0 评估序列化依赖后固定编码。记录校验值用于发现损坏，不充当内容真实性证明。
- 超范围偏移、非法状态、路径穿越、损坏记录和未来版本逐条隔离并报告，不能使整个存储目录无法打开，也不能覆盖未知版本数据。
- `FileSystem` 抽象支持短写、同步、截断、同文件系统 rename、目录同步、磁盘剩余空间和进程锁，并为故障注入提供替身。
- 读取租约、配额预留等进程内状态不直接恢复为有效对象；启动扫描重新计算占用，持久化 pin 和访问顺序。
- 暂存清理只针对 SDK 可确认所有权的文件，遵守年龄和活动任务保护；对未知文件隔离报告，不对调用方任意路径执行清理。

## 5. 里程碑与工作包

依赖主线：`M0 → M1 → M2 → M3 → M4 → M5`。Android 传输探针在 M0 提前做，正式接入在 M4
完成；协议服务器和体积工具贯穿各阶段。每阶段开始前确认上一阶段门槛，不以“接口已写完”替代验收。

### M0：验证关键假设，建立可执行契约

目标：排除平台网络、取消和体积方面的基础风险，明确后续实现的边界。

2026-10-26 实施记录：已建立服务器、CTest、两类 Android/JNI 探针和体积工具，契约细化见
[传输契约](transport-contract.md)、[API/存储契约](api-contract.md)，测量与缺测项见
[M0 报告](reports/m0-baseline.md)。HttpURLConnection 未通过全局凭证隔离，已增加独立 OkHttp 对照并调整设计方向；
Linux 与更多设备仍待验证，不能将 M0 标为全部完成。

M0 门槛：

- 测试延迟响应头、阻塞读取、背压等待和关闭竞态。建议实验目标为取消完成 p95 ≤ 1 秒、单次 ≤ 3 秒；每种情形至少
  100 次，记录设备、超时和失败次数。这是待验证目标，不能作为已承诺结果。
- 计时从控制请求被接受到后端确认无 I/O/缓冲访问，并分别记录 Paused 检查点完成时间；后者包含磁盘同步成本。
- 平台后端若无法满足取消或编码契约，先确定可行修复；需要改用网络后端时提交包含体积、许可证与集成成本的设计调整，再进入
  M1。不能将风险延后到 M4。
- 输出 `docs/reports/m0-baseline.md`，固定默认参数、依赖清单和数字预算。尚未测到的性能、体积、系统版本必须标注缺测。

| M1-04 | 手动重定向、循环/次数限制、HTTPS 降级限制、跨 origin 凭证处理、宿主请求提供入口               | M1-02        | 本地双 origin 和 HTTPS 场景验证凭证不泄漏；失败不写入拒绝的 body                          |

协议实施细则：

- 首次 200 从偏移 0 写入；续传遇 200 先关闭旧写入、重置暂存和元数据，再接收新内容。
- 206 严格检查起点、终点、总长、校验器和实际 body 字节数；合法局部响应未到末尾时继续后续区间。
- 弱 ETag、缺少强校验器默认重下；弱值不能进入 If-Range。首版不凭 Last-Modified 推断可安全续传。
- 416 必须进入重新确认流程；仅在版本、总长、本地长度和所需完整性验证均成立时进入正常完成流程，否则受控重下或协议错误。
- identity 之外的内容编码、相互矛盾的长度与非法整数范围拒绝；偏移运算检查溢出。
- 已知长度与预期长度均检查；未知长度必须由后端确认正常消息结束，不能用单纯“连接断开”代替成功。

M1 门槛：协议用例 T01～T07 通过 Linux 真后端测试；Linux 上进行实际超过 4 GiB
的传输与偏移校验。稀疏文件/模拟计数只覆盖边界逻辑，不能代替真实传输。仅预留构建目录不算测试交付。

```sh
cmake --build build/linux-debug --parallel
ctest --test-dir build/linux-debug --output-on-failure -L unit
ctest --test-dir build/linux-debug --output-on-failure -L contract
ctest --test-dir build/linux-debug --output-on-failure -L protocol
ctest --test-dir build/linux-debug --output-on-failure -L recovery
```

标签约定：`unit`、`contract`、`protocol`、`recovery`、`large_file`、`stress`
。常规协议集合不附带大文件耗时；大文件与压力任务显式选择，发布前全部执行。服务器由测试驱动启动/回收，禁止共享固定端口。

| 验证层次      | 触发时机        | 必须内容                                                              |
|---------------|-----------------|-----------------------------------------------------------------------|
| 每次变更      | 本地与 PR       | 受影响的单测、协议/恢复集合；现有版本与 JNI 烟测                      |
| Linux PR      | M1 起           | Debug 构建、常规协议；M2 起恢复；M3 起配额与竞态                      |
| Android PR    | M4 起完整化     | Debug AAR/APK、SDK/示例单测、设备 JNI/关键协议；Release 接入烟测      |
| 内存/并发诊断 | M2 起按改动触发 | Linux ASan/UBSan 与可用环境下的 TSan 分开运行，定位生命周期与数据竞争 |
| 夜间/候选发布 | M3 起           | 大文件、随机故障、反复开关、长稳；固定 seed 保证复现                  |
| 发布候选      | M5              | 全矩阵、真实 ENOSPC、设备生命周期、重启专项、体积与产物一致性         |

CI 平台在 M0 按仓库托管环境选择，不预设已存在的服务。没有设备的 CI 不能将设备任务视为通过，需提供独立设备执行记录。

## 8. 默认参数与待冻结决策

数值是实现起点。M0 报告给出最终配置与原因；面向宿主的可配置项要区分“缺省”“必须设置”“不能关闭的安全检查”。

| 项目                   | 计划起点                                                        | 冻结与验证                                                                                  |
|------------------------|-----------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| 活动下载               | 3 个                                                            | M0 定义硬上限，M3 验证调度及内存                                                            |
| 进度频率               | 最多每 200 ms 一次                                              | 状态/终态立即排队；终态不能被进度合并丢弃                                                   |
| 流式缓冲               | 每任务两个 64 KiB 块                                            | 3 个任务的该项排队预算为 384 KiB，另计网络/JNI/工作区和运行库；不当作进程总内存             |
| 检查点                 | 距上次提交 1 秒或新增 4 MiB，任一达到触发                       | M2 测试吞吐、同步延迟和恢复丢失窗口；暂停/发布/关闭单独触发                                 |
| 重试                   | 最多额外 3 次；1 秒起步、指数退避、随机抖动，基础退避上限 30 秒 | Retry-After 不因本地退避上限而提前重试；更长等待进入可持久化 RetryWaiting，验证重启后的预算 |
| 鉴权刷新               | 每次运行最多 1 次                                               | 与普通网络重试分开计数，避免 401/403 循环                                                   |
| 重定向                 | 每次请求链最多 5 跳并检测循环                                   | 跨 origin 清除鉴权；默认禁止 HTTPS 降级                                                     |
| 安全重下               | 协议不匹配后最多额外完整重下 1 次                               | 仍不匹配返回 ProtocolMismatch；摘要失败默认不自动重下                                       |
| 超时                   | 分别配置连接、响应头、读空闲与请求信息获取超时                  | M0 测定默认值，取消不能依赖无限等待；大文件不简单套用短的总时限                             |
| 配额/未知长度/暂存清理 | 要求宿主明确配置容量、单任务上限、保留时长                      | M3 确认参数校验与元数据计费上界，不能默认无限增长                                           |
| 摘要与记录格式         | 先固定接口，具体实现/编码待依赖评估                             | M0 候选与许可证/体积，M2 固定格式、兼容和未知版本行为                                       |
| Android 调度           | SDK 不绑定单一后台方式                                          | M4 按实际平台规则选择示例并记录依赖成本                                                     |

队列达到上限时，进度可合并，状态通知通过背压或明确的订阅错误处理；不能靠无限增长应对慢 executor。M0
明确事件容量、订阅数量和 `listTasks` 分页限制，M3 做慢消费者压力验证。

## 9. 体积与性能证据

体积工具在 M0 建立，在 M2 增加摘要实现后、M4 加入正式 Android 后端后和 M5 候选发布时复测。

- 最小宿主应与正式演示 App 分开；接入前后保持相同工具链、签名方式、ABI、压缩、资源与 R8 配置。Compose 演示
  App 的绝对 APK 大小不能代替 SDK 增量。
- 分别记录核心构建产物、`libfetchkit_jni.so`、AAR 全 ABI、单 ABI APK 与 SDK 接入增量，附依赖树和编译开关。
- 现有核心为静态库、JNI 为共享库；静态归档大小与最终 strip 后共享库不能混成同一指标。核心独立大小采用固定测量目标，另列
  JNI、STL 和新增依赖成本。
- `c++_static` 的成本计入实际 JNI 文件；若调整为共享运行库，必须同时计入新增运行库并验证宿主集成约束。
- `-Os/-Oz`、LTO、section GC 和符号裁剪逐项测量，比较吞吐、CPU、取消延迟、首包时间和内存；只有收益与回归结果清楚才启用。
- 未实现 Android curl 后端时明确缺测，不为体积比较额外扩大首版范围。

报告至少记录 Git 提交、构建命令、工具链、依赖版本、ABI、设备/API、strip/R8 状态、产物校验值和每项指标的原始数据。M0
形成数值预算；后续超过预算时说明来源并决定优化或更新预算。

## 10. 工作量与安排

以下为一名熟悉 C++/Android 的开发者、已有可用 Linux 环境与 Android
设备时的初步工程估算，包含对应自动化和文档，不是工期承诺。设备获取、外部评审、发布账号准备等等待时间另计；M0
结束后按实测重新估算。

| 阶段 | 预计人日 | 主要不确定性                                |
|------|----------|---------------------------------------------|
| M0   | 5～8     | 平台取消、工具链复现、设备与 HTTPS 测试环境 |

| M3   | 12～18   | 共享订阅、关闭竞态、配额和租约一致性        |
| M4   | 12～18   | JNI 生命周期、系统调度和设备差异            |
| M5   | 6～10    | 故障回归、外部接入与发布证据                |
| 合计 | 57～87   | 建议另留 20%～30% 风险余量                  |

加上风险余量，单人约 69～114 人日，按每周 5 个工作日约 14～23 周。多人投入可并行推进服务器/测试、核心/存储和
Android 探针，但 M0 契约、M2 发布恢复与最终集成仍在关键路径，不能按人数直接相除。

第一个实施周期建议覆盖 M0，按以下顺序提交：

1. `test: 建立原生测试与可控 HTTP 服务`：测试入口、固定内容和场景驱动；先保留原有版本/JNI 烟测。

3. `build: 增加 Android 接入体积对照工具`：固定最小宿主和产物测量口径。
4. `docs: 固定首版接口契约与关键假设结果`：记录参数、依赖、风险结论与 M1 的进入条件。

后续按工作包拆提交，每次提交包含相应验证。BUG 修复在提交或 PR 中记录原因、修复方式和复现用例；不将协议、存储、JNI、UI
堆成一个大提交。

## 11. 风险与处理出口

| 风险                                             | 最晚处理阶段 | 判断与处理                                                     |
|--------------------------------------------------|--------------|----------------------------------------------------------------|
| Android 取消停顿连接不及时、透明解码无法控制     | M0           | 以探针数据定方案；不符合契约则调整实现或提交后端设计变更       |
| 共享任务的取消、暂停、租约关闭语义不清           | M0           | API 契约先写可观察行为与交错测试，再实现 handle                |
| 工具链或依赖无法从干净环境复现                   | M0/M1        | 记录固定版本和来源；单独修复构建问题，避免混入功能改动         |
| 文件系统无法提供预期同步/原子性                  | M2           | 缩小平台保证并记录，采用保守恢复；不能跳过同步错误             |
| 配额、LRU 与租约跨线程出现不一致                 | M3           | 将资源变更串行化，配额预留与释放采用统一账本，故障点覆盖回滚   |
| 回调重入、慢 executor、JNI 迟到回调造成死锁/泄漏 | M3/M4        | 有界事件、generation、关闭屏障与重入测试；不在内部锁下调用宿主 |
| 后台方式与平台规则不匹配                         | M4           | 在目标 API 真机验证；宿主示例明确执行许可，SDK 不承诺常驻      |
| 实际接入体积超过预算                             | M2/M4/M5     | 分析依赖/运行库/符号贡献，实测优化；报告不能只展示核心文件     |
| 无法获得目标设备或完成重启/掉电测试              | M4/M5        | 缺测项列入发布记录，阻止对应保证；不能以模拟器或 kill 结果替代 |
| 签名 URL、请求头或备份泄漏私有信息               | M1/M4        | 使用合成凭证做脱敏断言，检查日志/记录/备份配置和跨 origin 请求 |
